# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A fully client-side React + Vite app that reads a **SCARED** questionnaire (child anxiety screening; 41 items across 2 pages) from photos/scans/PDFs, aligns each page to a known template, detects which answer circle is marked, and computes the total + 5 subscale scores. There is **no backend** — all image processing happens in the browser, by design (patient data must never leave the device). The product model is **auto-detect + human review**, not blind trust: answers are detected, low-confidence/missing ones are flagged, and the clinician confirms or fixes before using the score.

**The division of labour is deliberate: the human aligns, the computer reads.** Automatically locating a photographed form is the least reliable step in the pipeline; dragging four corners onto a ruled table takes a person ~5 seconds and essentially never goes wrong. Reading 123 cells is the opposite. So every page is reviewed on the user's **own photo** with the answer grid drawn over it (`GridOverlay`), with four draggable handles always available. Auto-alignment still runs and usually needs no correction — but because a human can always fix it, **alignment can no longer fail outright and no upload dead-ends.**

## Commands

```bash
npm run dev          # Vite dev server (default http://localhost:5173)
npm run build        # production build -> dist/
npm run preview      # serve the production build locally
npm run lint         # eslint
npm run sync-opencv  # re-vendor public/opencv.js from node_modules after bumping @techstark/opencv-js
```

There is **no test framework**. Verification is done by running the app (manually, or by driving headless Chrome with `puppeteer-core` against the dev server — Chrome is the only browser assumed installed; `puppeteer-core` is not in `package.json`, install it with `--no-save`).

For CV changes, the fastest reliable loop is to **drive `public/cvWorker.js` directly in Node**: copy `public/opencv.js` to a `.cjs` (the repo is `"type": "module"`) and run the worker under `vm.createContext` with `self`, `postMessage`, `ImageData` and `importScripts` stubbed. Synthetic pages can be generated by drawing marks onto the reference templates, then degrading them (grey cast, lighting gradient, noise, pixel shift, perspective warp) — that gives ground truth for hundreds of cases in seconds. **Still validate against real form photos before trusting a change**; synthetic noise is not camera noise.

`dist/` and `node_modules/` are **committed** (there is no `.gitignore`), so a `npm run build` or `npm install` dirties tracked files. Revert them unless the change is intended.

## Pipeline architecture (the big picture)

Upload → decode → **align to a known template** → detect marks → score. The order matters: detection only works because each page is warped to a canonical, fixed geometry. Data flows main-thread → worker as transferable `ImageData` buffers and back.

- **`src/utils/imaging.js`** — turns an uploaded file into canvases. PDFs render via `pdfjs-dist` (worker bundled locally as `pdfjs-dist/build/pdf.worker.min.js?url`, `annotationMode: ENABLE` so digitally-stamped PDFs are read — but see `pdfExtract.js`: rendering is **not** enough for a fillable form). Images decode via `createImageBitmap(blob, { imageOrientation: "from-image" })` with an `<img>` fallback. **HEIC** is decoded by `heic-to` (libheif wasm), which is **dynamically imported** so the ~3 MB chunk only loads when a HEIC actually arrives. Files are routed by MIME *and* extension *and* an ISO-BMFF brand sniff, because emailed iPhone photos routinely arrive with a stripped MIME type or even a `.jpg` name over HEIC bytes.
- **`src/utils/cvClient.js`** — main-thread owner of the single OpenCV Web Worker. Id-based request/response protocol; ships the reference templates + form geometry + `CONFIG` into the worker once via `initCv()`; exposes `processCanvas()` (auto-align) and `warpCanvas(canvas, corners, pageIndex, dest)` (align from four user-placed corners). Rebuilds aligned canvases from the worker's transferred pixel buffers.
- **`public/cvWorker.js`** — the actual OpenCV work, off the main thread.
  - *Align:* ORB feature-match → `findHomography` (RANSAC) → `warpPerspective` to canonical size. Returns the homography so the UI can place the overlay handles.
  - *Detect:* **template differencing** — flat-field the page, subtract the blank template's ink, count what is left per cell. Plus per-row local re-registration (`matchTemplate` over ±8 px) which absorbs page curl and residual perspective a single homography cannot.
  - Returns per-question `{selectedIndex, confidence, scores, reason}` plus a page-level `quality` object and the aligned image.
- **`src/utils/pdfExtract.js`** — reads answers straight out of a **digitally-filled** PDF's AcroForm field values, no CV involved. Fields are matched to questions **by geometry, not field name** (names vary by vendor; the widget rect is pinned to the printed cell, which we already have in the same 612×792 space). Page identity comes from which page's cells the widgets land in, and a page is only accepted if most widgets sit on known cells — so an unrelated fillable PDF falls through to the image pipeline instead of being misread. This exists because a widget with `/V` set but no `/AP` appearance stream **renders completely blank**: the answers are in the file, but rasterising loses them (measured: 0/20 before, 20/20 after).
- **`src/utils/homography.js`** — pure-JS 4-point perspective solve / apply / invert. The overlay draws on the main thread where OpenCV is unavailable, and needs a transform on every drag; a worker round-trip per pointer move would be far too slow.
- **`src/data/scaredForm.js`** — the form definition. Reuses `childQuestionnaireMap.js` (the 41×3 answer-cell boxes), adds question text, `CANON_SCALE`, `TABLE_QUADS` (the answer table's outer corners per page), the reference template images, and the scoring config (subscale labels + cutoffs, total cutoff).
- **`src/utils/score.js`** — total + subscale tally from a `{question: 0|1|2|null}` map.
- **`src/utils/flags.js`** — shared "needs review" logic (`flaggedForPage`, `flagStats`, `LOW_CONFIDENCE = 0.4`). Used by the overlay banner and the global status bar so they always agree.
- **`src/components/GridOverlay.jsx`** — **the primary page view.** The user's photo with the 123 answer cells projected onto it through the current homography, coloured by detection state, plus four draggable corner handles (arrow keys nudge). Releasing a handle re-runs detection. Clicking a cell sets/confirms/clears an answer. Also carries the alignment badge, the "N items need review" banner, the page-number selector, and the "too grainy to trust" warning.
- **`src/components/PageReview.jsx`** — the same review UI over the *rectified* image, reachable per page via "Straightened view". Useful as an alignment sanity check; no longer the default.
- **`src/components/ManualEntry.jsx` + `ReferenceImages.jsx`** — the **manual-entry mode**, a second path that bypasses the CV pipeline entirely. The app has a "Scan a form" / "Enter by hand" toggle: the hand mode renders all 41 items as a blank on-screen form (three targets per row, `0`/`1`/`2` keys answer and advance) scored by the same `computeScore`, with an optional side-by-side viewer for the user's own photo/scan/PDF (decoded via `fileToCanvases`, **no OpenCV, no alignment**). Scanned answers can be copied into it as a starting point.
- **`src/App.jsx`** — orchestration + UI state: recognition gating, completeness/duplicate detection, the sticky status bar, per-page state (answers, user-confirmations, corners, alignment mode), and `alignFromCorners()`.

## Non-obvious constraints (read before changing these areas)

### OpenCV / worker

- **OpenCV is loaded as a static `<script src="/opencv.js">`, NOT imported.** `@techstark/opencv-js` is a ~10 MB eval-laden emscripten bundle; importing it through Vite's module/dep pipeline **hangs the page during evaluation**. It's vendored to `public/opencv.js` and loaded via `importScripts` in the worker. The npm dependency exists only as the source for that vendored copy — run `npm run sync-opencv` after upgrading it. `cvClient`/the worker detect readiness by **polling `cv.Mat`**, not the one-shot `onRuntimeInitialized` callback (which races and can leave the promise pending forever).
- **Two opencv.js functions silently do nothing.** Both cost real debugging time; the symptom is a transform that appears to run but changes no pixels.
  - **`mat.clone()` ALIASES the source** — same data pointer at every size, verified. Even `cv.bitwise_not(c, c)` on the "copy" mutates the original. Use `const d = new cv.Mat(); src.copyTo(d);` — `copyTo` into a *fresh* Mat does allocate.
  - **`srcRoi.copyTo(dstRoi)` is a no-op** when the destination is an ROI view (it reallocates rather than writing through). To write a sub-rectangle, copy rows via `dst.data.set(src.data.subarray(...), offset)`.
- **`public/cvWorker.js` is a plain classic worker in `public/` (not bundled by Vite)** so it can use `importScripts` and stay self-contained. Its align/detect logic is **intentionally duplicated** from the data model rather than imported; if you change detection thresholds or the algorithm, update the worker **and** keep `cvClient.js`'s `CONFIG` in sync. Every *tuning* threshold is read from `cfg`, so `CONFIG` is the one place to change them. Structural constants stay inline in the worker (the flat-field kernel, the `260`/`880` row-strip span, the ink-bbox cutoff) — those encode the form's geometry, not a knob to turn.

### Mark detection (the part that is easy to break)

The form's "circles" are the **letter `o`** — a ~13 px glyph, ~55 dark pixels, inside a ~104×36 px cell, with the table rules 0–4 px outside it (the bottom rule is *adjacent*). Consequences, all measured:

- **Never score raw darkness.** A *blank* cell already reads `darkFraction` 0.0144–0.0181, the baseline varies 26% between columns of the same row, and a 5 px misregistration pulls a rule in worth +0.057. There is no stable threshold in that metric; this is why detection differences against the template instead.
- **`tolerancePx` must stay 1.** It dilates the template's ink to absorb misregistration, but at ≥2 it closes the printed `o` ring into a solid disc and the detector goes **completely blind to filled-in marks** (they score 0.000). Verified.
- **Score the whole cell, not a window around the target.** People do not mark consistently — checks land beside the circle, lines get drawn through or under it, circles are drawn much larger than it. A tight window missed all of those. The cell is scored (inset `cellInsetPx` to clear the rules) but **normalised by the small `padPx` window area**, which keeps the dynamic range wide.
- **Do not add a `MORPH_OPEN` despeckle.** It looks like the obvious noise fix and it destroys the marks: a drawn underline lost 100% of its pixels, a line through the target 86%. Speckle is removed by a 3×3 median on the ink map plus a `minBlob` connected-component area filter, which preserve thin strokes.
- **Detection is style-agnostic by construction.** It never asks "is this a checkmark?", only "is there ink here the blank form cannot explain?". Keep it that way — mark style cannot be controlled.
- **Three noise floors, because one is not enough.** `minInk` (absolute), median+MAD over all cells, and p95 of the *known-blank* cells (only one cell per row can be the answer, so the 2nd/3rd ranked cells of every row are guaranteed blank — 82 samples per page). `quality.noisy` additionally fires on `blanksAboveFloor` and on `pageResidual`, which measures unexplained ink in the **question-text half of each answer row** — registered like the cells but incapable of holding a mark, so anything there is pure image noise. Measuring the *whole page* instead false-alarms on every shifted page, since only the row bands get re-registered.
- **`confidence` folds in absolute strength, not just separation.** `(top − sec)/top` alone returns 1.0 for a barely-there mark with a clean runner-up, so marginal reads were never flagged — wrong for an auto-detect + human-review product.

### Geometry

- **Two coordinate spaces, easy to mix up.** Answer-cell boxes in `childQuestionnaireMap.js` are in the form's **612×792 PDF space** (multiply by `CANON_SCALE` = 2 to index the aligned canvas). `TABLE_QUADS` in `scaredForm.js` are already in **1224×1584 canonical pixels**. The reference templates (`src/assets/reference/blank_p0.png`, `blank_p1.png`) are the blank form rendered at 2× and serve as both the alignment templates and the canonical geometry.
- **The overlay warps the grid onto the photo, not the photo onto the grid.** Same homography, inverted. The photo stays crisp and un-resampled so the clinician reviews actual pen strokes; detection still rectifies internally. Handles go on the **answer table's** corners (crisp ruled intersections) rather than the page's, which in a photo are often shadowed or cropped off.
- **`MAX_DIMENSION` is 2200, not 1600.** A page photographed in landscape fills only part of the frame; at 1600 the form landed ~1000 px tall and had to be *upsampled* into the 1584 px canonical size, smearing 2 px pen strokes. A/B on a 4032×3024 landscape photo: 1600 → 18/20 detected, 2200 → 20/20.

### UI / build

- **Tailwind v4** (`@tailwindcss/postcss`). The `content` array in `tailwind.config.js` is **ignored** by v4 — sources are declared in `src/index.css` via `@import "tailwindcss"` + `@source`. If newly added utility classes silently don't apply, that's why (and a dev-server restart forces a rescan). `index.css` also pins `color-scheme: light`.
- **Recognition gating.** RANSAC inliers separate a real SCARED page (hundreds) from a different document (single digits): `RECOGNIZE_MIN` (25) and `STRONG_INLIERS` (60) in `App.jsx`; the worker's own `minInliers` is a separate, looser gate. A page below `RECOGNIZE_MIN` is **not a dead end** — it renders the grid overlay with a note, and aligning it by hand brings it into the score. Missing and duplicate pages are detected and surfaced. Uploads **append**, so a 2-page form can be uploaded one photo at a time.
- **Review/scoring is live and local.** A user click on a cell counts as confirmation (clears its flag, shown in a distinct "confirmed by you" style); scoring updates immediately; nothing is persisted or exported.
- **`heic-to` is LGPL-3.0** (it bundles libheif). Keep it a dynamic `import()` — a static import both bloats the main bundle and risks the same Vite evaluation problem as opencv.js.

## Deploy

Vite outputs to `dist/` (not `build/`). `vercel.json` sets `framework: vite` + `outputDirectory: dist`. The vendored `public/opencv.js` and `public/cvWorker.js` are copied to the dist root and served at `/opencv.js` and `/cvWorker.js`, which is where the runtime loads them from (`import.meta.env.BASE_URL`-prefixed).
